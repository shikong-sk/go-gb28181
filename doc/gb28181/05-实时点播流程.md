# GB/T 28181-2016 实时点播流程

## 点播概述

实时点播是视频监控系统的核心功能，通过SIP INVITE/ACK/BYE流程建立媒体会话，使用RTP传输视频流。

## 基本点播流程

### 流程图（B2BUA模式）

```
客户端              SIP服务器/媒体服务器              设备
  │                      │                           │
  │ ──── INVITE ────────>│                           │ (1)
  │                      │ ──── INVITE ─────────────>│ (2)
  │                      │                           │
  │                      │ <─── 100 Trying ──────────│ (3)
  │                      │                           │
  │                      │ <─── 200 OK ──────────────│ (4)
  │ <─── 200 OK ─────────│                           │ (5)
  │                      │                           │
  │ ──── ACK ───────────>│                           │ (6)
  │                      │ ──── ACK ─────────────────>│ (7)
  │                      │                           │
  │ <══════════════ RTP 流 ════════════════════════│ (8)
  │                      │                           │
  │ ──── BYE ───────────>│                           │ (9)
  │                      │ ──── BYE ─────────────────>│ (10)
  │                      │                           │
  │                      │ <─── 200 OK ──────────────│ (11)
  │ <─── 200 OK ─────────│                           │ (12)
```

### 流程说明

1. **客户端发起INVITE请求**
   - 包含SDP描述，指定接收媒体的地址和端口
   - Subject头域指定点播的设备和通道

2. **服务器转发INVITE请求**
   - B2BUA模式：生成新的INVITE请求
   - 代理模式：直接转发

3. **设备返回100 Trying**
   - 表示正在处理请求

4. **设备返回200 OK**
   - 包含SDP描述，指定发送媒体的地址和端口
   - 包含SSRC标识

5. **服务器转发200 OK**
   - B2BUA可能修改SDP内容

6. **客户端发送ACK**
   - 确认会话建立

7. **服务器转发ACK**

8. **设备发送RTP流**
   - 按照协商的编码格式发送

9. **客户端发送BYE**
   - 结束会话

10. **服务器转发BYE**

11. **设备返回200 OK**

12. **服务器转发200 OK**

## 多客户端点播同一设备

### 流程说明

当多个客户端同时点播同一设备时，B2BUA服务器负责媒体流分发：

```
客户端A ─────┐
             │
客户端B ─────┼──> SIP服务器/B2BUA ────> 设备
             │
客户端C ─────┘
```

### SSRC处理

1. 设备发送一个RTP流（SSRC=1000000001）
2. B2BUA接收后分发到多个客户端
3. 每个客户端收到的SSRC可能不同

### 媒体流分发

- B2BUA接收设备发送的媒体流
- 复制媒体包发送给各客户端
- 需要处理RTCP反馈

## 错误处理

### 486 Busy Here

设备忙，可能有其他客户端正在点播：

```sip
SIP/2.0 486 Busy Here
Via: SIP/2.0/UDP 192.168.1.100:5060;rport;branch=z9hG4bK-xxx
From: <sip:34020000002000000001@3402000000>;tag=e3719a0b
To: <sip:34020000001320000001@3402000000>
Call-ID: xxx
CSeq: 1 INVITE
Content-Length: 0
```

### 488 Not Acceptable Here

编码格式协商失败：

```sip
SIP/2.0 488 Not Acceptable Here
Via: SIP/2.0/UDP 192.168.1.100:5060;rport;branch=z9hG4bK-xxx
From: <sip:34020000002000000001@3402000000>;tag=e3719a0b
To: <sip:34020000001320000001@3402000000>
Call-ID: xxx
CSeq: 1 INVITE
Content-Length: 0
```

## 会话超时处理

### 客户端超时

- 客户端异常断开，服务器应发送BYE结束会话
- 基于RTP超时检测（建议60秒无RTP包判定超时）

### 设备超时

- 设备停止发送媒体流
- 服务器检测到后通知客户端

## TCP传输模式

### 适用场景

- UDP端口受限的NAT环境
- 需要可靠传输的场景

### SDP配置

```
m=video 6000 TCP/RTP/AVP 96
a=setup:active
a=connection:new
```

### TCP连接建立

1. 如果 `a=setup:active`，客户端主动连接设备
2. 如果 `a=setup:passive`，设备等待客户端连接

## 注意事项

1. **INVITE事务处理**
   - INVITE需要ACK确认
   - ACK不应终止INVITE事务（RFC 3261）

2. **Subject头域**
   - 格式：`设备ID:通道ID,平台ID:通道ID`
   - 用于标识点播关系

3. **SDP方向属性**
   - 请求：`a=recvonly`（平台只接收）
   - 响应：`a=sendonly`（设备只发送）

4. **CSeq递增**
   - 同一Call-ID内的请求CSeq递增
   - BYE的CSeq = INVITE的CSeq + 1

5. **SSRC唯一性**
   - 每个会话使用不同的SSRC
   - SSRC冲突时需要重新生成
